# MC模组服务器配置：内存怎么分、JVM 参数怎么调，整合包到底该买几核几G的机器

模组服卡，很少单纯是因为机器买得太便宜。

更常见的情况是内存给少了、JVM 参数还在用默认值、`server.properties` 里的视距顺手拉到 12，然后一台 4 核 8G 的机器在五个人的整合包服上把 TPS 压到 15。这三件事都算"配置"，但一个是买机器的配置，另外两个是服务端的配置，搞混了就一定会绕远路。

下面把两条线拆开讲：模组加载方式怎么改变资源需求、服务端文件里真正该动的是哪几个值，以及算完之后该选什么档位的机器。

## 模组服和纯净服，从加载方式上就不是一类东西

纯净服跑 Paper 或 Purpur，玩法靠插件，插件是贴在服务端外面的东西。模组服不一样，它靠 Forge、NeoForge 或 Fabric 这类加载器，模组以 `.jar` 的形式塞进服务端，而且服务端和客户端的模组列表必须严格对应——版本、加载器版本、模组版本，任何一处不匹配，玩家就连不进来。

这件事带来了一个直接后果：模组服的资源曲线是往上叠的。每个模组都会往 Java 堆里加载自己的类、贴图和处理逻辑，200 个模组光初始化就能吃掉好几个 G 的内存，再加上模组新增的实体、方块、机器和世界生成逻辑，运行时占用比纯净服高一个量级。

官方文档和几个托管商的公开说明里都提到同一条经验：MC 1.18 以上的版本消耗大约是 1.16 的两倍、1.12.2 的三倍。也就是说，你要配一台模组服，先确认版本——1.12.2 的整合包和 1.20 的整合包，同样的机器跑出来是两个结果。

## 内存：模组服最先爆掉的地方

分配内存的规则就三条，但很多人第一条就写错：

- `-Xms` 和 `-Xmx` 设成**相同值**。不相等的话，堆会在运行中反复伸缩，GC 停顿会变多，玩家端表现为周期性卡顿。
- 不要超过物理内存的 80%。剩下的要留给操作系统、世界存档 I/O 和 JVM 自身开销。
- 模组服的 `-Xmx` 不要照抄纯净服的数值。50 个模组的包和 200 个模组的包不是一回事。

具体给多少，整合包作者和几家托管商的公开建议基本落在同一个区间：

| 模组规模 | 建议分配给服务端 | 参考在线人数 |
| --- | --- | --- |
| 50 个模组以内（轻量整合包） | 4–6 GB | 2–5 人 |
| 50–150 个模组（中型整合包） | 8–12 GB | 5–10 人 |
| 200 个模组以上（ATM9、ATM10 这类） | 12–16 GB 起 | 3–8 人 |
| RLCraft 这类实体密度极高的包 | 6–8 GB | 10 人以内 |

注意最后两行的对比：大型整合包吃内存，不是因为人多，而是因为模组多。三个人的重整合包比八个人的原版服要的内存还多，这是模组服最反直觉的一点。

## CPU：只看单核，核心数往后排

Minecraft Java 版服务端的主逻辑跑在一个叫 Server thread 的线程里——方块更新、实体 AI、红石逻辑、玩家交互，全部串行处理。多核能帮上忙的地方只有区块生成、光照计算和网络包压缩这些可以并行的部分。

结论很直接：决定卡不卡的是单核性能，不是核心数。一台 4 核 5.0GHz 的机器，开模组服的表现通常好过 8 核 2.5GHz 的便宜机器。挑机器的时候先看 CPU 型号的单核跑分，再看核数。

雨云游戏云可选的高主频机型不少，官方论坛的测试帖里给过部分机型的单核数据，整理出来大致是这样：

| CPU 机型 | 单核参考（论坛实测口径） | 适合的模组服场景 |
| --- | --- | --- |
| i9-14900K | CPU-Z 单核约 895 分，Geekbench 6 单核约 2830 分 | 200+ 模组的大型整合包、群组服 |
| Ryzen 9950X | 5.8GHz，Zen5 架构 | 1.20+ 高版本模组服、基岩服 |
| W9-3495X | 单核约 620–700 分，对标 7950X | 1.20+ 模组服、多开场景 |
| Ryzen 7950X | CPU-Z 单核 670–700 分 | 高版本整合包 |
| Ryzen 5900X | CPU-Z 单核 450–520 分 | 中高版本模组服、小型群组服 |
| Xeon Gold 6146 | 4.2GHz，中等单核水平 | 模组量不大的插件服 |
| Platinum 8259CL | 多核强、单核弱 | 低版本模组服、纯净服 |
| E5-2666v3 | 2.9GHz，单核垫底 | 低版本小服、挂机服 |

## server.properties：真正影响体验的其实只有几项

这个文件里参数上百个，日常需要动的没几个：

- `view-distance`：视距，默认给到 10 以上对模组服就是负担。官方给的参考基准是纯净/基岩服 6、模组服 5、Fabric 服 5。
- `simulation-distance`：模拟距离，比视距更吃性能，建议比 `view-distance` 小 2。
- `max-players`：别虚标。写 20 人和真能带 20 人是两回事。
- `online-mode`：正版验证。公开服建议保持 `true`，不然改客户端就能进。
- 端口默认 25565，改过端口的话记得在控制台同步放行。

想再细调，`paper.yml` 里有实体合并、红石频率限制这些选项，但默认值已经够用，新手先别急着改。

## JVM 参数：默认启动参数就是给服务器找罪受

社区里公认的起点是 Aikar's Flags——针对 MC 服务端调过的 G1GC 参数组，目的是把 GC 停顿压到几十毫秒级别。下面这套是按 8G 堆内存写的，按你的实际内存改 `-Xms` 和 `-Xmx` 两个值就行：


java -Xms8G -Xmx8G -XX:+UseG1GC -XX:+ParallelRefProcEnabled \
  -XX:MaxGCPauseMillis=200 -XX:+UnlockExperimentalVMOptions \
  -XX:+DisableExplicitGC -XX:+AlwaysPreTouch \
  -XX:G1NewSizePercent=30 -XX:G1MaxNewSizePercent=40 \
  -XX:G1HeapRegionSize=8M -XX:G1ReservePercent=20 \
  -XX:G1HeapWastePercent=5 -XX:G1MixedGCCountTarget=4 \
  -XX:InitiatingHeapOccupancyPercent=15 \
  -XX:G1MixedGCLiveThresholdPercent=90 \
  -XX:G1RSetUpdatingPauseTimePercent=5 -XX:SurvivorRatio=32 \
  -XX:+PerfDisableSharedMem -XX:MaxTenuringThreshold=1 \
  -jar server.jar nogui


Java 版本别搞错：1.17 及以上用 Java 17，1.20.5 之后的新版本和不少新整合包建议 Java 21，1.16 及以下才用 Java 8。版本对不上，服务端直接启动失败。

## 几个被问得最多的问题

**2 核 4G 能开模组服吗？**
能，但要看你装多少模组。50 个模组以内、三五个人的包，2 核 4G 勉强够用，前提是视距别超过 6、别装区块加载器。200 个模组的包就别为难它了。

**内存给够了还是卡，问题在哪？**
先看单核占用。如果单核跑满、内存还有余量，那是 Server thread 瓶颈，只能换更高主频的 CPU，加内存没用。反过来内存吃满、GC 频繁触发，才轮到加内存。还有一种情况是磁盘 I/O——玩家跑图时"卡区块"，多半是存储跟不上，SATA 盘换 NVMe 就没了。

**模组服必须要独立公网 IP 吗？**
不是必须。NAT 机型加端口映射一样能连，只是玩家拿到的地址会带端口号，分享起来麻烦一点。想省事就加购独立 IP。

**要不要装一堆优化插件？**
插件越多，主线程负担越重。模组服本身已经够重了，优化方向应该放在 JVM 参数、视距和区块预生成上，而不是再往服务端里塞东西。装模组也一样，改刷怪逻辑、改实体生成的模组最容易在跑图时把 TPS 拽下来，装之前想清楚。
